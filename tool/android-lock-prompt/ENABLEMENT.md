# Synthetic provider enablement contract (verified from sources; the device behavior is UNVERIFIED)
- credentials 1.3.0 (pinned) already ships androidx.credentials.provider.*; no extra dependency. Provider classes compile against the real classes.jar.
- Manifest contract (developer.android.com/identity/sign-in/credential-provider): service with permission android.permission.BIND_CREDENTIAL_PROVIDER_SERVICE, intent-filter action android.service.credentials.CredentialProviderService, meta-data android.credentials.provider -> xml with capability androidx.credentials.TYPE_PUBLIC_KEY_CREDENTIAL (res/xml/lockfx_provider.xml). Without the capability the provider is skipped ("Service does not have the required capabilities", CredentialManagerServiceImpl, android14-release).
- API 34 enabled providers = Settings.Secure credential_service, a ":"-separated list of flattened component names (CredentialManagerService.getEnabledProvidersForUser, android14-release); primary = credential_service_primary. The framework's own setter needs WRITE_SECURE_SETTINGS.
- The runner uses `adb shell settings put secure credential_service "<existing>:app.otpanda/app.otpanda.fixture.SyntheticProviderService"`, reads it back, and restores the old value at the end.
UNVERIFIED on a device: that the shell settings write is honored on the API 34 google_apis image, that the Google provider and this one coexist in the selector, the selector tap and confirm path, and whether a confirm step needs another needle text. If the settings write fails the harness stops with ENABLE failure (readback); the fallback is Settings > Passwords, passkeys & accounts via uiautomator, not built.
